# Hammer Trading Company Connection Audit

Date: 27 July 2026

## Scope

This audit traced customer UI actions to Next.js API routes, Prisma models, authentication guards, production data, and external integrations. It also compared the latest local source with the current Vercel production deployment.

## Executive Result

The core store is database-backed and substantially connected:

- Products, variants, images, categories, brands, cart tracking, checkout, stock deduction, orders, order timelines, bulk print, QR codes, admin authentication, Google customer authentication, and private customer/admin chat have working code paths.
- All literal frontend `/api/...` references found in the source have matching API routes.
- The latest local production build passes.
- Production public APIs are responding and the live database is returning products and room-package data.

The following features are incomplete, disconnected, misleading, or not populated.

## P0: Blocks A Promised Core Flow

### 1. Delivery OTP Is Generated But Not Delivered

Checkout creates and hashes a real OTP, then calls `sendSms()`. The SMS function is still a TODO and only writes a server log. The API does not return the OTP, which is correct for security, but without an SMS provider the customer cannot receive it.

Impact:

- QR + OTP delivery confirmation cannot complete for a real customer.
- The printed QR can open the confirmation page, but the customer has no delivered OTP.

Evidence:

- `app/api/checkout/route.ts` calls `sendSms()` for the delivery OTP.
- `lib/integrations.ts` has an unimplemented SMS provider.
- `SMS_API_KEY` exists locally but is not read by the implementation.

Required connection:

- Connect a real transactional SMS provider.
- Store provider message ID, delivery state, attempts, and last error.
- Add retry handling and an admin resend-OTP action with rate limits.

### 2. Latest Local Fixes Are Not On Production

The current production deployment is `READY`, but it was created before the final local fixes. Local source files were updated after the active deployment.

Impact:

- Production does not contain every fix listed in the latest local audit/build.
- Local verification and live behavior can differ.

Required action:

- Deploy the current source after the Vercel/Codex deployment limit resets.
- Run the same authenticated smoke tests against the new production deployment.

## P1: Visible Features That Do Not Perform Their Advertised Job

### 3. Product WhatsApp Quick Order Uses A Demo Number

The product detail quote component reads `NEXT_PUBLIC_WHATSAPP_SUPPORT_NUMBER`, but that variable is not defined in the local environment. It falls back to the sample number from the code.

Production HTML was checked and the live product WhatsApp link currently contains that fallback number.

Impact:

- Product-page WhatsApp inquiries can go to the wrong number.
- Footer/contact WhatsApp can be correct while product-page WhatsApp is wrong because they use different configuration sources.

Required connection:

- Use the database-backed `whatsapp_number` setting everywhere.
- Remove the hardcoded phone fallback from customer actions.

### 4. Courier Booking Is Mocked

Leopards, TCS, PostEx, Trax, BlueEX, and Local Riders return generated booking/tracking values without calling provider APIs.

Impact:

- "Book courier" does not create a shipment with the courier.
- Tracking numbers generated by the app are not courier tracking numbers.
- No courier webhook updates order delivery status.

Required connection:

- Implement provider-specific authenticated adapters.
- Save request/response IDs and normalized status.
- Add webhook verification, tracking sync, cancellation, and label retrieval.

### 5. WhatsApp Notifications Are No-Ops

`sendWhatsApp()` only logs the payload. Checkout order confirmation and abandoned-cart recovery call it and can report success without sending a customer message.

Impact:

- Order confirmation WhatsApp is not delivered.
- Abandoned-cart recovery can be logged as sent even when nothing was sent.

Required connection:

- Connect WhatsApp Business templates through a real provider.
- Return an explicit delivery result instead of silently succeeding.

### 6. Payment Settings Are Not Connected To Checkout

Admin settings include payment methods, bank transfer details, Easypaisa QR, and JazzCash QR. Checkout only exposes:

- Cash on delivery
- A label explicitly called "Bank transfer placeholder"

There is no payment proof upload, gateway transaction, payment webhook, or automatic reconciliation. Easypaisa/JazzCash settings are not consumed by checkout.

Impact:

- Admin can configure payment fields that customers never see.
- Non-COD orders cannot be automatically verified.

### 7. Coupon Preview And Backend Coupon Logic Disagree

The checkout API correctly validates database coupons with dates, limits, customer/product/category scope, amount/percentage discounts, maximum discount, and free delivery.

The checkout screen calculates its preview using only hardcoded `HAMMER500`.

Impact:

- A valid admin-created coupon can show the wrong total before submission.
- The final database order total may differ from the visible checkout summary.

Required connection:

- Add a server-side quote endpoint for cart, delivery, package discounts, tax, and coupon.
- Use that same quote result for the displayed total and final checkout transaction.

### 8. Wishlist Is A Static Recommendation Page

`WishlistItem` exists in Prisma, but there is no customer wishlist API and no add/remove implementation in product cards or product detail.

The `/wishlist` page always displays featured/best-seller recommendations.

Impact:

- "Wishlist" is visible in navbar, account, and footer but customers cannot save products.

### 9. Customer Review Creation Is Missing

Product queries load approved `Review` rows and admin can moderate them. However:

- There is no customer review creation API/form.
- Delivery confirmation stores rating/review text only inside an activity-log metadata object.
- It does not create a `Review` record.
- The product page displays review heading/placeholder text rather than actual review content.

Live product search currently reports rating `0` for the returned products.

Required connection:

- On verified delivery, create a pending review linked to customer, product, and order item.
- Add customer edit window and admin moderation.
- Render approved review content, rating distribution, and verified-purchase status.

## P2: Partially Connected Or Operationally Incomplete

### 10. Two Separate Room/Service Systems Are Running

Legacy flow:

- Customer `/home-service`
- `RoomPackage` and `RoomServiceRequest`
- Admin `/admin/room-packages` and `/admin/room-services`

New platform flow:

- Customer `/services`, `/packages`, and `/projects`
- `HomeService`, `ProductPackage`, `ServiceBooking`, and `Project`
- Admin `/admin/website`

Both architectures have database/API code, but their data and workflows are separate.

Production content check:

- Legacy room packages: 1
- Published new services: 0
- Published new product packages: 0
- Published projects: 0

Impact:

- Customers see a populated room-service flow and empty advanced service/package/project pages.
- Admin has two places to manage closely related features.

Required decision:

- Migrate legacy room data into the new platform models and keep one management flow, or clearly separate "Room consultation" from "Catalog services/packages".

### 11. Advanced Website Manager Has Empty Production Content

Production currently returns zero records for:

- Managed navigation
- Managed homepage sections
- Services
- Product packages
- Projects

The navbar/footer correctly fall back to built-in links, and the homepage uses fallback copy. This is missing content, not a database outage.

The homepage section manager is also only partially consumed: the storefront currently reads the `complete-solutions` key for heading/description, while arbitrary section records do not automatically render new homepage blocks.

### 12. Several Admin Settings Are Stored But Ignored

Connected settings include company/contact/footer values, logo, social URLs, theme colors, and policy text.

Settings with no complete runtime consumer include:

- `favicon`
- `currency` (formatting is hardcoded to PKR)
- `tax_settings`
- `invoice_prefix` and `order_prefix`
- global `low_stock_threshold`
- `payment_methods`
- `bank_transfer_details`
- `easypaisa_qr` and `jazzcash_qr`
- `notification_settings`
- `default_theme`
- `animations_enabled`
- `maintenance_enabled` and `maintenance_message`
- `announcement_bar`
- `about_us`, `faq`, `delivery_policy`, and `warranty_policy`

The navbar announcement remains hardcoded. Order and invoice prefixes are also hardcoded.

### 13. Shipping Settings And Checkout Rules Use Different Sources

The shipping information page displays `default_delivery_charges` and `free_delivery_amount` from system settings.

Actual checkout delivery pricing uses `DeliveryRule` records. Changing the settings-page values does not change checkout pricing.

If no active delivery rule exists, the current database calculation returns a zero charge with "No delivery rule".

### 14. Returns Is Support-Ticket Management, Not A Return Portal

The customer returns page is policy text only. Admin `/admin/returns` renders the general support-ticket manager.

There is no structured customer return request with:

- order-item selection
- reason/evidence
- pickup or drop-off choice
- approval/rejection workflow
- refund transaction
- replacement shipment

Delivery issue reporting can create an audit event, and admin can move an order to returned/refunded through support, but the complete customer return workflow is not connected.

### 15. Email Delivery Can Silently Succeed Without A Provider

SMTP code exists and local SMTP variable names are present. However, when SMTP is unavailable or not configured, `sendEmail()` logs and returns instead of reporting a failed delivery to the calling feature.

Affected flows include:

- Password reset
- Admin email change verification
- Admin password-change notification
- Order email
- Abandoned-cart recovery

Production SMTP delivery was not intentionally triggered during this audit, so provider delivery remains unverified.

### 16. Support Fallback Storage Is Not Production-Persistent

The legacy support-ticket/chat APIs fall back to JSON files under `data/` when PostgreSQL fails.

That is useful locally, but Vercel serverless filesystem storage is not a permanent shared database. A production database failure should return a controlled error or queue the request in durable storage, not report a persistent success from local JSON fallback.

The newer private `/account/messages` and `/admin/messages` system correctly requires the database and enforces customer isolation.

### 17. Storefront Database Fallback Can Hide Connection Instability

The storefront first uses the Neon serverless SQL path, then Prisma, then static fallback products. Production observability contains one recent `Neon catalog transaction timed out` event on a product route.

Impact:

- The page can still return `200`, but temporarily show fallback/stale catalog data instead of revealing that live inventory could not be read.

Required hardening:

- Add database latency metrics and alerts.
- Avoid a 15-second wait before fallback.
- Mark fallback responses internally and avoid using fallback prices/stock for checkout.

### 18. Media Storage Is Not Connected To Object Storage

Product, hero, and room-package image uploads are optimized, but can still be stored as data URLs in PostgreSQL. The generic Media manager accepts URLs rather than providing a real upload pipeline.

Missing production media layer:

- Vercel Blob, Cloudinary, or S3
- responsive derivatives
- upload progress/retry
- object deletion lifecycle
- image CDN transformations

### 19. Dormant Database Features

Models exist without a complete customer/admin workflow:

- `ComboOffer` and `ComboOfferItem`
- `RecentlyViewed`
- `ReportSnapshot` generation

These should either be completed and exposed or removed in a future backward-compatible cleanup after confirming no production data depends on them.

## Local Versus Production Environment

- Production Google OAuth is connected and redirects to Google with the correct production callback.
- Local `.env` does not contain Google OAuth variables, so local Google sign-in cannot mirror production without pulling/configuring those values.
- The product WhatsApp public variable is absent and the live page proves the fallback number is being used.
- `SMS_API_KEY` and `COURIER_API_KEY` exist locally but their implementations do not consume them.

## Verified Connected Areas

- PostgreSQL product catalog
- Parent products and variants
- Variant price/SKU/stock selection
- Product image gallery
- Cart persistence and guest/customer merge
- Package-aware cart lines
- Checkout transaction and stock deduction
- Dynamic backend coupon validation
- Delivery-rule calculation
- Orders, order timeline, status and stock restoration
- Bulk order slip/QR printing
- Admin product/order/customer/inventory CRUD
- Google customer OAuth in production
- Admin password authentication and protected admin routes
- Private customer/admin messaging with per-user conversation isolation
- Contact/quote persistence while PostgreSQL is available
- Hero/banner management code path
- Legacy room-service request and room-package management
- Responsive customer/admin layouts

## Recommended Fix Order

1. Connect SMS OTP delivery and resend/audit flow.
2. Deploy the latest verified local source.
3. Replace product WhatsApp fallback with the database setting.
4. Connect real courier APIs and status webhooks.
5. Add one server-side checkout quote endpoint and remove hardcoded coupon preview.
6. Finish payment methods or hide incomplete methods.
7. Implement wishlist and verified review creation/rendering.
8. Unify the two room/service management systems and publish real content.
9. Wire or remove inactive admin settings.
10. Replace JSON/data-URL fallbacks with durable queues and object storage.
